# SG-001 — Potential missing authorization check

| | |
|---|---|
| **Name** | `missing-authorization` |
| **Default severity** | warning (info for low-confidence findings) |
| **Confidence** | high / medium / low (per finding) |
| **Tags** | security, authorization, access-control |

## What it detects

An exported contract function (a `pub fn` in a `#[contractimpl]` block, or any function of a
`#[contractimpl]` trait implementation) that performs a **sensitive operation** while neither the
function itself nor any helper it calls performs an **authorization check**.

Sensitive operations, from most to least severe:

| Operation | Example | Confidence |
|---|---|---|
| Contract upgrade | `env.deployer().update_current_contract_wasm(hash)` | high |
| Token transfer *out of* the contract | `token.transfer(&env.current_contract_address(), &to, &amount)` | high |
| Write to a privileged key (admin, owner, operator, minter, …) | `storage().instance().set(&DataKey::Admin, &a)` | high |
| Any other storage write (`set`, `remove`, `update`, `try_update`) in a function taking an `Address` | `storage().persistent().set(&DataKey::Balance(user), &x)` | medium |
| Any other storage write | `storage().instance().set(&DataKey::Counter, &n)` | low, reported as **info** |

Privileged keys are recognised by the key's own name — the enum variant, struct name or symbol
(`DataKey::Admin`, `symbol_short!("OWNER")`) — not by the enum type or the values passed in, so
`GovernorKey::OperationId(id)` is not privileged and `DataKey::Balance(admin)` is not either.

Recognised authorization checks:

* `address.require_auth()` and `address.require_auth_for_args(args)` on any address;
* calls to helpers whose name looks like an authorization helper — starts with `require`, `enforce`,
  `ensure`, `assert`, `check`, `verify` or `only` and contains `auth`, `role`, `owner` or `admin`
  (e.g. `require_admin(&env)`, `ownable::enforce_owner_auth(&e)`);
* access-control attribute macros such as `#[only_owner]`, `#[only_admin]`, `#[only_role(..)]`,
  `#[has_role(..)]` (OpenZeppelin Stellar contracts);
* any function listed in `auth-functions` in `stellar-guard.toml` or passed with `--auth-fn`.

Helpers are followed transitively through the crate (free functions, `Self::f()` / `Type::f()`
calls, and `self.f()` methods).

Skipped functions: `__constructor` (runs once at deploy), `__check_auth` (custom account
authorization) and initializer-named functions, which are covered by [SG-005](SG-005.md).

## Why it matters

Exported functions can be invoked by anyone with arbitrary arguments. Without `require_auth`, any
account can, for example, withdraw another user's funds, take over the admin role, or replace the
contract code.

## Example

```rust
#[contractimpl]
impl Vault {
    pub fn withdraw(env: Env, user: Address, amount: i128) {
        // ⚠ SG-001: missing `user.require_auth()`
        token_client(&env).transfer(&env.current_contract_address(), &user, &amount);
    }
}
```

Fixed:

```rust
pub fn withdraw(env: Env, user: Address, amount: i128) {
    user.require_auth();
    token_client(&env).transfer(&env.current_contract_address(), &user, &amount);
}
```

## Known limitations

* **False positives:** intentionally permissionless functions (counters, keeper "poke" hooks,
  public registration that is safe by design). Suppress with
  `// stellar-guard-ignore SG-001 -- <reason>` or list them under `ignore-functions`.
* **False negatives:** the rule only checks that *some* authorization happens, not that the *right*
  address is authorized (e.g. `attacker.require_auth()` followed by a write to the victim's balance
  passes). Helpers are resolved by name only; auth in another crate is invisible unless listed in
  `auth-functions`.
* Calls through traits, closures stored in variables, or macros that expand to storage writes are
  not followed.

## Options

```toml
[rules.SG-001.options]
ignore-functions = ["increment", "poke"]   # intentionally permissionless
privileged-keys  = ["Oracle", "FeeRecipient"]  # extra privileged storage-key words
```
