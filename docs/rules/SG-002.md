# SG-002 — Suspicious storage type for application state

| | |
|---|---|
| **Name** | `storage-tier-misuse` |
| **Default severity** | warning |
| **Confidence** | high / medium (per finding) |
| **Tags** | security, storage, state |

## What it detects

Soroban offers three storage tiers:

| Tier | Lifetime | Typical use |
|---|---|---|
| `persistent()` | archived when TTL expires, restorable | balances, positions, per-user data |
| `instance()` | shares the contract instance's TTL; loaded on **every** call | small contract-wide config (admin, token address) |
| `temporary()` | **deleted permanently** when TTL expires | allowances with expiry, nonces, caches |

The rule reports two patterns:

1. **Long-lived state written to temporary storage** — a `temporary().set(..)` /
   `.update(..)` whose key mentions a word such as `Balance`, `Admin`, `Owner`, `Supply`, `Config`,
   `Paused`, `Role`, `Position`, `Debt`, `Collateral`, `Vote`, `Registry` …
   Confidence is **high** for balance/admin/owner/supply keys and **medium** otherwise.
2. **Per-key data written to instance storage** — an `instance().set(..)` whose key is built with
   arguments, e.g. `DataKey::Balance(addr)` or `DataKey::LastClaim(user)` (medium confidence).
   Writes inside `__constructor` are skipped: the deployer sets them once, so the set is bounded.

Keys are matched by the key's own name — the enum variant, struct name or symbol literal — split
into words (`TotalSupply` → `total`, `supply`). Values passed into the key are ignored, so
`StorageKey::MinterStats(config.epoch)` does not match `config`. A local variable used as a key is
followed to the closest preceding `let` (`let key = DataKey::Balance(a);`).
Keys containing words that are *meant* to expire — `Allowance`, `Nonce`, `Cache`, `Session`,
`Lock`, `Expiration`, `Signature`, `Cooldown`, `Pending`, … — are never reported.

### Growing collections in instance storage

A `Map` / `Vec` read from instance storage, extended with caller-supplied entries
(`members.set(member, weight)`, `list.push_back(addr)`) and written back under the same single key
is also reported (medium confidence), unless the function checks its `len()`. The entry grows
without bound just like per-user keys.

## Why it matters

* A balance in temporary storage silently disappears once its TTL lapses — funds are lost and
  cannot be restored.
* An admin address in temporary storage expiring leaves the contract without an admin (or lets
  someone re-initialize it).
* Per-user entries in instance storage make one ledger entry grow with every user. It is read and
  written on every invocation and has a size limit, so costs rise for everyone and the contract can
  eventually stop working.

## Example

```rust
fn write_balance(env: &Env, owner: &Address, amount: i128) {
    // ⚠ SG-002: balances must not expire
    env.storage().temporary().set(&DataKey::Balance(owner.clone()), &amount);
}
```

Fixed:

```rust
fn write_balance(env: &Env, owner: &Address, amount: i128) {
    let key = DataKey::Balance(owner.clone());
    env.storage().persistent().set(&key, &amount);
    env.storage().persistent().extend_ttl(&key, LIFETIME_THRESHOLD, BUMP_AMOUNT);
}
```

## Known limitations

* Detection is name-based: a balance stored under `DataKey::X` is not detected, and a key named
  `ConfigCache` is treated as ephemeral.
* The storage tier must be visible at the call site (`env.storage().temporary()` directly or via a
  local variable); storage handles passed as parameters are not tracked.

## Options

```toml
[rules.SG-002.options]
sensitive-keys = ["Ticket", "Escrow"]   # extra words meaning "long-lived"
ignore-keys    = ["Quote"]              # extra words meaning "fine to expire"
```
