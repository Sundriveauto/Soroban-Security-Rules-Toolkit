# SG-004 — Potentially unbounded iteration

| | |
|---|---|
| **Name** | `unbounded-iteration` |
| **Default severity** | warning (info for caller-supplied sizes) |
| **Confidence** | high / low (per finding) |
| **Tags** | security, denial-of-service, resource-limits |

## What it detects

Loops in Soroban crates whose length is not bounded by the contract:

| Source of the collection / bound | Example | Confidence |
|---|---|---|
| Loaded from storage (directly, via a local variable, or via a crate helper that reads storage and returns a `Vec`/`Map`) | `for m in read_members(&env).iter()` | high, **warning** |
| A `Vec` / `Map` / `Bytes` parameter of an exported function | `for r in recipients.iter()` | low, **info** |
| An integer parameter of an exported function used as a range end or `while` bound | `for i in 0..count` | low, **info** |

Caller-supplied sizes are reported as `info`: an oversized input only makes the caller's own
transaction fail, so this is a hardening hint rather than a denial of service against others.
Parameters of `__constructor` (set by the deployer) and `__check_auth` (bounded by the transaction)
are not treated as caller-controlled.

Loop forms: `for` loops, `while` loops whose condition compares against such a value, and iterator
chains (`.iter()` / `.into_iter()` / `.keys()` / `.values()` followed by `map`, `filter`, `fold`,
`for_each`, `sum`, `count`, `collect`, …).

Not reported when the function bounds the value:

* the name appears in a comparison inside an `if` condition, `match` guard or assertion macro
  (`if items.len() > MAX { panic!() }`, `assert!(limit <= MAX)`);
* the iterator is limited with `.take(n)`, `.step_by(..)`, `.first()` or `.nth(..)`;
* the stored collection is **capped where it grows**: some storage-writing function in the crate
  compares `.len()` of a variable with the same name against a bound
  (`if members.len() >= MAX_MEMBERS { return Err(..) }`);
* the loop is over a literal range or a locally constructed collection.

## Why it matters

Soroban transactions have hard limits on CPU instructions, memory and ledger entries read. If a
stored list can grow without limit — for example, anyone can join a member list — then any function
that iterates the whole list will eventually exceed those limits and fail on every call. If that
function is the only way to withdraw or distribute funds, those funds are locked forever.
Caller-supplied sizes let a single caller force arbitrarily expensive work.

## Example

```rust
pub fn distribute(env: Env, amount_each: i128) {
    let members: Vec<Address> = env.storage().persistent().get(&DataKey::Members).unwrap();
    for m in members.iter() {           // ⚠ SG-004
        client.transfer(&env.current_contract_address(), &m, &amount_each);
    }
}
```

Fixed (paginate):

```rust
pub fn distribute(env: Env, start: u32, limit: u32, amount_each: i128) {
    assert!(limit <= MAX_BATCH, "limit too large");
    let members: Vec<Address> = env.storage().persistent().get(&DataKey::Members).unwrap();
    let end = start.saturating_add(limit).min(members.len());
    for i in start..end {
        client.transfer(&env.current_contract_address(), &members.get_unchecked(i), &amount_each);
    }
}
```

Better still, store each member under its own key (`DataKey::Member(addr)`) so no single entry grows.

## Known limitations

* Write-side caps are matched by variable name only. A cap enforced under a different variable
  name, or by a separate counter, is not seen; suppress such findings with a reason.
* Whether a list is only extended by a trusted admin is not analyzed.
* A bound check anywhere in the function counts, even if it happens after the loop.
* Recursion is not considered.
