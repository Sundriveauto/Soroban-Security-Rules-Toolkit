# SG-009 — Custom account `__check_auth` does not verify the signature

| | |
|---|---|
| **Name** | `weak-check-auth` |
| **Default severity** | error |
| **Confidence** | high / medium (per finding) |
| **Tags** | security, authorization, account-abstraction |

## What it detects

A custom account's `__check_auth(env, signature_payload, signatures, auth_contexts)` that:

* **verifies nothing:** neither it nor any crate helper it calls invokes a signature check
  (`ed25519_verify`, `secp256r1_verify`, `secp256k1_recover`, BLS pairing checks, or any function
  whose name contains `verify`) or hands authorization to other addresses (`require_auth`,
  `require_auth_for_args`, `delegate_auth`). High confidence when it also never uses
  `signature_payload` or `signatures`, medium otherwise;
* **verifies a signature over something else:** it calls a signature check but never uses
  `signature_payload`, so the signature is not bound to the transaction being authorized
  (medium confidence).

Accounts that delegate (`delegate_auth`, `signer.require_auth()`) without reading the payload are
not reported: the delegated accounts verify their own signatures.

## Why it matters

Every `require_auth()` on a custom account's address is answered by its `__check_auth`. If it
returns `Ok(())` without checking a signature over `signature_payload`, anyone can authorize
transfers, approvals and upgrades on the account's behalf. A signature over a fixed or
attacker-chosen message can be replayed for any transaction.

## Example

```rust
fn __check_auth(env: Env, signature_payload: Hash<32>, signature: Signature, _ctx: Vec<Context>)
    -> Result<(), Error>
{
    // ⚠ SG-009: the key is checked, the signature is not
    if !env.storage().instance().has(&DataKey::Signer(signature.public_key)) {
        return Err(Error::UnknownSigner);
    }
    Ok(())
}
```

Fixed:

```rust
    if !env.storage().instance().has(&DataKey::Signer(signature.public_key.clone())) {
        return Err(Error::UnknownSigner);
    }
    env.crypto().ed25519_verify(&signature.public_key, &signature_payload.into(), &signature.signature);
    Ok(())
```

## Known limitations

* **False negatives:** any verifier call counts, even one that checks the wrong key or runs on only
  some paths. Checks of `auth_contexts` (spend limits, allowed contracts) are not analysed.
* **False positives:** accounts that authorize purely from on-chain state by design (for example a
  timelock that only executes scheduled operations) and use no `require_auth`. Suppress with a
  reason.
